# [가이드] 범용 아키텍처 결정 기록 가이드 (Universal ADR Guide)

---

## 1. 개요 및 목적
본 문서는 모든 소프트웨어 프로젝트에서 발생하는 **핵심 아키텍처 의사결정의 배경(Context), 선택한 대안(Decision), 그리고 그에 따른 트레이드오프(Consequences)**를 체계적으로 기록하여 아키텍처 부채를 통제하는 표준 지침입니다.

AI 에이전트는 주요 기술 선택이나 구조적 변경 시 임의로 결정하지 않으며, 반드시 본 가이드에 따라 ADR을 작성하고 Architecture Squad 및 담당 엔지니어의 승인을 획득해야 합니다.

---

## 2. ADR 라이프사이클 및 작성 원칙
- **상태 정의 (Status)**:
  - `PROPOSED`: 제안됨 (검토 및 승인 대기 중)
  - `ACCEPTED`: 승인됨 (구현 착수 가능)
  - `SUPERSEDED`: 새로운 상위 결정으로 대체됨 (대체한 ADR 번호 명시 필수)
  - `DEPRECATED`: 폐기됨
- **트레이드오프 솔직성**: 모든 기술적 선택에는 비용이 따릅니다. 이점(Pros)뿐만 아니라 감수해야 하는 복잡도나 제약사항(Cons)을 누락 없이 명시해야 합니다.

# [템플릿] 아키텍처 결정 기록 실행 양식 (ADR Template)
*신규 아키텍처 의사결정 시 아래 양식을 복사하여 기록합니다.*

```markdown
## ADR-{{번호}}: {{의사결정 제목}}
- **상태 (Status)**: PROPOSED | ACCEPTED | SUPERSEDED | DEPRECATED
- **의사결정자 (Deciders)**: {{Architecture Squad, Lead Engineer}}
- **결정 일자**: {{YYYY-MM-DD}}

### 1. 배경 및 문제 정의 (Context)
- 해결하려는 기술적 또는 비즈니스적 문제는 무엇인가?
- 어떤 제약 조건(비용, 성능, 일정, 보안, 기존 시스템 호환성)이 있는가?

### 2. 의사결정 내용 (Decision)
- 어떤 기술, 패턴, 아키텍처를 채택하였는가?
- 검토했던 다른 대안들(Alternatives)은 무엇이며, 왜 기각되었는가?

### 3. 결과 및 트레이드오프 (Consequences)
- **긍정적 영향 (Pros)**: {{예: 테스트 격리성 극대화, 모듈 간 결합도 완화}}
- **부정적/중립적 영향 (Cons)**: {{예: 인터페이스 정의 증가, 초기 셋업 복잡도}}
- **후속 조치 사항 (Follow-ups)**: {{이 결정으로 인해 요구되는 후속 작업}}
```

# [기본 탑재] 공통 기반 아키텍처 결정 목록

### ADR-0001: OpenAI 하네스 엔지니어링 및 심포니 오케스트레이션 도입
- **상태**: ACCEPTED
- **배경**: 단순 프롬프트 기반의 개발 방식은 모델 드리프트와 잦은 환각을 유발하며, 생성된 코드를 사람이 수동 패칭하는 병목을 야기함.
- **결정**: "담당 엔지니어는 조율(Steering)하고 에이전트는 실행(Execution)한다"는 하네스 엔지니어링을 채택하고, 결정론적 가드레일, 자가 치유 폐루프(Error Envelope), 지속적 문서 동기화(Doc-Gardening) 체계를 전면 도입함.
- **결과 및 트레이드오프**:
  - **장점**: 수동 코딩 개입 없이 고품질 소프트웨어를 안정적으로 자율 생산 가능.
  - **단점**: 프로젝트 초기 CI 린터 및 테스트 하네스 스캐폴딩 셋업 비용이 발생함.

### ADR-0002: 헥사고날 아키텍처 기반 도메인 격리 채택
- **상태**: ACCEPTED
- **배경**: 에이전트가 코드를 작성할 때 비즈니스 로직과 외부 데이터베이스/외부 API 호출을 강하게 결합시켜 단위 테스트 작성이 어려워지는 현상을 방지해야 함.
- **결정**: 핵심 도메인 로직을 외부 인프라와 완전히 격리하고 Port/Adapter 패턴을 강제하며, 정적 아키텍처 검증 도구(ArchUnit 등)로 의존성 방향을 검증함.
- **결과 및 트레이드오프**:
  - **장점**: 데이터베이스나 외부 연동 라이브러리가 변경되어도 도메인 로직과 단위 테스트를 100% 온전하게 보존할 수 있음.
  - **단점**: 계층 분리로 인해 인터페이스 및 DTO 매핑 보일러플레이트 코드가 다소 증가함.

### ADR-0003: 장애 탄력성 및 서킷 브레이커(Circuit Breaker) 패턴 의무화
- **상태**: ACCEPTED
- **배경**: 외부 LLM API 또는 써드파티 서비스의 지연 및 장애가 시스템 전체로 전파되는 연쇄 장애(Cascading Failure)를 방지해야 함.
- **결정**: 모든 외부 연동 구간에 기본 타임아웃(3초 이내)과 서킷 브레이커, 안전한 Fallback 응답 로직을 의무적으로 구현하도록 규정함.
- **결과 및 트레이드오프**:
  - **장점**: 외부 서비스가 일시적으로 중단되어도 핵심 서비스 가용성 99.9%를 방어할 수 있음.
  - **단점**: 기능별 Fallback 시나리오를 사전에 기획하고 별도의 단위 테스트를 작성해야 함.
