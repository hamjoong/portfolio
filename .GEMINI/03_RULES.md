# [가이드] 범용 하네스 엔지니어링 협업 및 운영 규정 (Collaboration Rules)

---

## 1. 개요 및 목적
본 문서는 담당 엔지니어(사람)와 AI 에이전트 간의 **협업 거버넌스, 변경 관리 기준, 그리고 에이전트 자율 개발 라이프사이클을 통제하는 핵심 운영 규정**을 정의합니다.

---

## 2. 하네스 엔지니어링 5대 핵심 운영 원칙 (Core Rules)

### 1) 수동 패칭 금지 원칙 (Fix the Harness, Never Patch Code)
에이전트가 작성한 코드에 결함이 발생했을 때, 사람이 직접 코드를 수정하지 않는다. 실패의 원인이 된 **린터 룰, 정적 타입, 인터페이스 스키마, 테스트 케이스 등 하네스 환경을 보강**하여 에이전트가 자체 수정(Self-Repair)하도록 시스템을 개선한다.

### 2) 결정론적 검증 우선 원칙 (Deterministic Rails over Prompt Guesswork)
프롬프트 상의 모호한 자연어 당부에 의존하지 않는다. 컴파일러 검사, AST 린터, 아키텍처 제약 도구, 자동화된 단위 테스트를 통해 코드 품질을 기계적으로 차단하고 강제한다.

### 3) 무경고 원칙 (Zero Tolerance Policy)
모든 린트 및 빌드 단계에서 `Warning 0, Error 0` 정책을 엄격히 적용한다. 사소한 경고(Warning) 1건도 잠재적 결함으로 간주하여 빌드를 즉시 중단한다.

### 4) 2단계 승인 관문 통제 (Two-Gate Steering)
- **[Gate 1] 스펙 승인 관문**: `01_PRD.md` 및 `08_ADR.md` 작성을 완료하고 사람의 명시적 승인을 득하기 전까지는 코드 작성을 시작하지 않는다.
- **[Gate 2] 릴리즈 승인 관문**: 자동화된 보안 및 품질 파이프라인, 카나리 텔레메트리 검증을 통과한 후 사람의 최종 승인을 거쳐 프로덕션에 배포한다.

### 5) 원자적 작업 단위 제한 (Atomic Task Scoping)
에이전트의 컨텍스트 윈도우 과부하와 환각(Hallucination)을 방지하기 위해 한 번의 작업 세션당 범위를 제한한다.
- 단일 태스크당 수정 파일 수: **최대 5개 이하**
- 단일 태스크당 추가/수정 코드 라인: **최대 200줄 이하**

# [템플릿] 프로젝트별 협업 및 변경 규정 (Project Rules Template)
*신규 프로젝트 착수 시 프로젝트의 특수한 환경에 맞춰 작성하는 양식입니다.*

```markdown
---
project_name: "{{프로젝트명}}"
version: "1.0.0"
governance_lead: "Lead Engineer & Governance Squad"
last_updated: "{{YYYY-MM-DD}}"
---

# 1. 의사결정 및 커뮤니케이션 프로토콜
- **모호성 해결 절차**: 요구사항이나 인터페이스가 불명확한 경우 임의로 추측하여 구현하지 않는다. 반드시 최소 2가지 이상의 실행 가능한 대안과 각각의 장단점을 정리하여 담당 엔지니어에게 선택을 요청한다.
- **주석 작성 기준**: '어떻게(How)' 동작하는지는 코드로 자명하게 드러내고, 주석은 반드시 해당 로직이 '왜(Why)' 필요한지 비즈니스 배경을 중심으로 명확한 한국어로 작성한다.

# 2. 변경 관리 기준표 (Change Management Matrix)

| 변경 항목 | 위험도 | 선행 승인 주체 | 필수 산출물 |
| :--- | :--- | :--- | :--- |
| **비즈니스 요구사항 / 신규 기능** | 중간 ~ 높음 | Lead Engineer | `01_PRD.md` 갱신 |
| **코어 아키텍처 / 스택 변경** | 높음 | Lead Engineer | `08_ADR.md` 신규 수립 |
| **API 인터페이스 / DB DDL** | 중간 | Architecture Squad | `02_TRD.md` 갱신 |
| **내부 리팩토링 / 성능 튜닝** | 낮음 | Governance Squad | 단위 테스트 100% 통과 (기능 변경 0) |

# 3. 프로젝트 금지 조항 (Strict Prohibitions)
1. 소스 코드 내 시크릿(API 키, 토큰, 패스워드) 평문 하드코딩 금지
2. 보안 스캔(SCA) 승인을 받지 않은 신규 외부 라이브러리 임의 추가 금지
3. 리팩토링이나 성능 최적화 진행 중 기존 기능의 인터페이스나 동작을 변경하는 행위 금지
4. 경고를 무시하기 위한 린트 비활성화 주석(`eslint-disable`, `@SuppressWarnings` 등) 사용 금지
5. 환경 변수는 `.env` 또는 Secret Manager로 관리한다.
6. 코드 저장소에 직접 포함하지 않는다.
7. 로그에 민감정보를 출력하지 않는다.
8. Secret Manager : `.env` 파일 사용을 지양하고, AWS Secret Manager 또는 HashiCorp Vault를 연동하여 런타임에 주입한다.
```
