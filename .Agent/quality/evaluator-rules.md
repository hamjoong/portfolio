# 평가자 규칙 및 AI Slop 방지 기준 (Evaluator Rules)

이 문서는 OpenAI 하네스 엔지니어링의 핵심인 **생성자(Generator)와 평가자(Evaluator)의 분리 원칙**에 따라 에이전트가 코드를 작성한 후 독립적인 평가자 관점에서 품질과 아키텍처 불변성(Mechanical Invariants)을 엄격히 채점하는 규칙을 정의합니다.

---

## 1. 생성자-평가자 분리 메커니즘 (Generator vs Evaluator)

* **생성자 관점 (Implementation Mode)**:
  - 사용자의 요구사항을 빠르게 코드로 변환하고 비즈니스 기능을 완성하는 데 집중합니다.
* **평가자 관점 (Evaluation Mode)**:
  - 코드가 정상 실행되더라도 **"AI Slop(겉보기만 그럴싸하고 구조적 규칙을 어긴 코드)"**이 섞이지 않았는지 아래의 5대 기계적 체크리스트로 가혹하게 검증합니다.
  - 평가를 통과하지 못하면 작업 완료로 판정하지 않고 즉시 재수정(Feedback Loop)에 들어갑니다.

---

## 2. 5대 기계적 불변성(Invariants) 채점표

| 검증 항목 | 허용 기준 (Pass) | 불합격 기준 (Fail) | 조치 사항 |
| :--- | :--- | :--- | :--- |
| **1. 경계 격리 (Isolation)** | 오직 작업 대상 단일 프로젝트 폴더 내 파일만 변경 | 타 프로젝트(`devcodehub` / `shoppingmall` / 등) 파일이 1줄이라도 변경됨 | 즉시 타 프로젝트 파일 롤백 |
| **2. 비밀정보 노출 (Zero Trust)** | `.env` 커밋 제외 / API Key / 비밀번호 코드 내 하드코딩 0건 | 코드 / 주석 / 설정 파일에 실제 Key / Secret 노출 | 하드코딩 즉시 제거 및 환경 변수화 |
| **3. 코드 가독성 및 규모** | 함수 길이 50줄 이하 / 클래스 300줄 이하 / 중첩 깊이 3 이하 | 50줄 초과 거대 함수 / 콜백/if 중첩 깊이 4 이상 | 함수 분리 및 조기 반환(Early Return) 리팩토링 |
| **4. 주석 품질 (Why 중심)** | 비즈니스 사유 / 아키텍처 결정 배경을 한국어로 설명 | "i를 1 증가시킨다" 식의 뻔한 What 설명 또는 영문 기계번역 | "왜(Why)" 관점의 자연스러운 한국어 주석으로 전면 재작성 |
| **5. 기술 스택 강요 여부** | 기존 프로젝트의 언어 / 스타일 / 빌드 도구 100% 존중 | 사용자가 요청하지 않은 신규 프레임워크나 복잡한 인프라 강제 도입 | 오버엔지니어링 코드 삭제 및 원복 |

---

## 3. 평가 실패 시 피드백 루프 (Automated Feedback Loop)

```
[코드 생성 완료]
       ↓
[평가자(Evaluator) 채점 실행]
       ↓
  [불합격 발견?] ──(YES)──> [원인 파악 및 자가 교정 (Self-Correction)]
       │                                     │
      (NO) <─────────────────────────────────┘
       ↓
[scripts/validate-workspace.sh 기계식 검증 통과]
       ↓
[최종 사용자 보고 완료]
```
