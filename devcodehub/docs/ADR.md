# [ADR] Architecture Decision Records

## 1. PII 마스킹 처리 유틸리티 도입
- **상태**: Accepted
- **컨텍스트**: SECURITY.md 가이드라인에 따라 로그에 사용자 이메일, ID 등 개인정보(PII)가 평문으로 노출되는 것을 방지해야 함.
- **결정**: `MaskingUtil`을 `global.util` 패키지에 도입하고, 모든 서비스 레이어의 로깅 지점에서 이를 적용함.
- **결과**: 보안 사고 예방 및 보안 감사 대응력 향상.

## 2. 채팅 도메인 복합 인덱스 전략 적용
- **상태**: Accepted
- **컨텍스트**: 실시간 채팅 메시지가 수만 건 이상 쌓일 경우, 특정 방의 메시지를 최신순으로 가져오는 쿼리의 성능 저하 예상.
- **결정**: `chat_room_id`와 `created_at`을 묶는 복합 인덱스(`idx_chat_room_created_at`)를 추가하여 정렬 및 필터링 성능을 최적화함.
- **결과**: 방별 최신 메시지 조회가 인덱스를 타도록 하여 데이터가 늘어도 조회 비용이 급증하지 않도록 함. (측정 수치는 아직 없음)

## 3. JPA N+1 방어 전략 표준화 (EntityGraph)
- **상태**: Accepted
- **컨텍스트**: 게시판 및 댓글 조회 시 작성자(User) 정보를 가져오는 과정에서 발생하는 N+1 쿼리 병목 확인.
- **결정**: `CommentRepository` 등에 `@EntityGraph`를 적용하여 연관 엔티티를 Eager Fetch 하도록 명시함.
- **결과**: 쿼리 횟수 감소로 인한 DB 부하 경감 및 응답 속도 개선.

## 4. Supabase Native API 기반 스토리지 연동
- **상태**: Accepted
- **컨텍스트**: Java AWS SDK v1과 Supabase S3-compatible API 간의 서명(Signature) 불일치 이슈로 인해 운영 환경에서 이미지 업로드 실패.
- **결정**: SDK 의존성을 제거하고, Supabase에서 제공하는 Native Storage API(HTTP POST)와 `service_role` JWT를 직접 사용하여 통신하도록 변경함.
- **결과**: 외부 라이브러리 의존성 없이 안정적인 파일 업로드 구현 및 서명 관련 보안 취약점 원천 차단.

## 5. 채팅 메시지는 DB에 즉시 저장하고 Redis는 사용하지 않음
- **상태**: Accepted
- **컨텍스트**: 기존에는 메시지를 DB에 바로 저장하면서 Redis 큐(Write-behind)에도 넣었고, 큐를 읽는 쪽은 역직렬화에 항상 실패해 조용히 버려졌다. 같은 메시지가 Redis로 두 번 발행되기도 했다.
- **결정**: Write-behind 큐·스케줄러를 제거한다. 저장은 DB에 즉시 한다. 이후 Redis Pub/Sub 전파 기능도 제거했다(운영이 무료 서버 1대라 꺼진 채로 남은 코드였다). 서버를 여러 대로 늘릴 때 외부 브로커를 다시 도입한다.
- **결과**: 저장·전달 경로가 하나로 단순해지고 메시지 유실·중복 위험이 사라진다. 대신 다중 인스턴스 채팅 전파는 지원하지 않는다.

## 6. WebSocket(STOMP) 인증을 채널 인터셉터에서 수행
- **상태**: Accepted
- **컨텍스트**: HTTP 보안 필터는 STOMP 프레임에 적용되지 않아, 인증 없이 연결해 남의 채팅방·알림 채널을 구독하거나 발신자를 위조할 수 있었다.
- **결정**: `StompAuthChannelInterceptor`에서 CONNECT 시 JWT를 검증하고 SUBSCRIBE마다 참여자/본인/역할 채널 여부를 검사한다. 발신자는 클라이언트 값 대신 인증 정보(Principal)를 쓴다. 게스트는 소켓에 연결하지 않는다.
- **결과**: 채팅·알림이 인증된 사용자 범위로 제한된다.

## 7. 결제 검증 정책 (PortOne 테스트 결제)
- **상태**: Accepted
- **컨텍스트**: 결제 ID 재사용, 구독 결제의 금액·상태 미검증, 타인 결제 도용, 결제 없이 크레딧을 올리는 API가 가능했다. 프론트는 V2 SDK만 쓰지만 서버에는 V1·V2 검증이 모두 있었다.
- **결정**: V1·V2 Strategy를 모두 유지하되 응답을 `PaymentInfo`로 정규화한다. 결제 ID는 `credit_transactions.payment_id` 유니크로 1회만 허용, 금액은 서버 가격표와 비교, 소유자는 `customData.loginId`/`customer.id`로 대조한다. 결제 없이 충전·구독하는 API는 삭제한다. 환급은 실결제 금액 기준 일할 계산(`REFUND`)이다.
- **결과**: 중복 지급·위변조·도용 경로가 막힌다. 모바일 리다이렉트는 V2(`paymentId`)와 V1(`imp_uid`) 쿼리를 모두 처리한다(실기기 확인 필요).

## 8. 크레딧·정산은 행 잠금으로 직렬화, AI 호출은 트랜잭션 밖
- **상태**: Accepted
- **컨텍스트**: 크레딧 증감이 읽고-고치고-쓰기라 동시 요청에서 유실되고, AI 호출(수십 초) 동안 트랜잭션이 DB 커넥션을 점유했다.
- **결정**: 크레딧 증감과 시니어 매칭/정산은 `PESSIMISTIC_WRITE` 행 잠금으로 직렬화한다. AI 리뷰는 "검사 → 트랜잭션 없이 AI 호출 → 짧은 트랜잭션에서 정산"으로 나눈다.
- **결과**: 중복 차감·중복 정산을 막고 커넥션 점유 시간을 줄인다.
